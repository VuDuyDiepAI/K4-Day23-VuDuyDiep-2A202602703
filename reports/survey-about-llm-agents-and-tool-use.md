# LLM Agents and Tool Use: Foundations, Methods, Evaluation, and Open Problems

## TL;DR

- Tool use by language models moved from separate prompted tricks to a single agent loop: ReAct interleaves reasoning traces with actions and reports absolute success-rate gains of 34% on ALFWorld and 10% on WebShop with one or two in-context examples [1][2], while Toolformer showed that tool invocation (which API, when, which arguments) can be learned self-supervised from a handful of demonstrations per API [3], and MRKL framed tools as discrete modules around a language model [4].
- The production interface stabilised as JSON-schema tool specifications plus models fine-tuned to detect when a call is needed and to emit arguments adhering to the signature [5], a convention mirrored by Gemini function declarations with parallel and compositional calling [6]; the Model Context Protocol then generalised tool access into an open client/server standard [7] that OpenAI also consumes as a tool source, with human approval required by default [8], and that complements agent-to-agent delegation via A2A and Agent Cards [9][10].
- Scale is the second organising theme: ToolBench covers 16,464 RESTful APIs [11], hierarchical retrievers with self-reflection recover from unusable candidate APIs [12], and newer work compresses candidate sets before prompting [13] or selects tool sets jointly rather than scoring tools in isolation [14].
- Evaluation, not modelling, is the bottleneck: outcome-based environments such as WebArena and OSWorld score functional correctness yet still show large human/agent gaps [15][16], and validity audits show contamination and weak tests inflate headline numbers, cutting SWE-agent's resolution rate from 12.47% to 3.97% on a cleaned issue set [17][18].
- Safety is now a first-class design constraint: agent benchmarks report prompt-injection success rates up to 84.30% [19] and covert exfiltration through a legitimate web-fetch tool at 79.7% [20], while scoped authorization reduced harmful executions to zero in a paired-replay study [21] and step-level guardrails cut harmful tool invocations by 65% [22].

## Background

Early work on tool use grew out of two separate lines. One line gave the model an environment to act in: WebGPT fine-tuned GPT-3 to answer long-form questions with a text-based browsing environment that outsourced retrieval to a search API, using behaviour cloning followed by rejection sampling against a reward model trained on human preferences, and its best model's answers were preferred by humans 56% of the time over those of human demonstrators and 69% of the time over the highest-voted Reddit answer [23]. WebShop pushed the same idea toward realistic interaction, building a simulated e-commerce site with 1.18 million products and 12,087 crowd-sourced instructions; its best model reached a 29% task success rate against 9.6% for rule-based heuristics and 59% for human experts [24]. The other line gave the model explicit modules: MRKL proposed a "modular, neuro-symbolic" architecture in which discrete knowledge and reasoning modules complement neural models, instantiated in AI21's Jurassic-X [4].

Those lines converged in prompting-based agents. ReAct generates reasoning traces and actions in an interleaved manner, so that traces plan and repair while actions query external sources such as a Wikipedia API, and it reports absolute success-rate gains of 34% (ALFWorld) and 10% (WebShop) over imitation- and reinforcement-learning baselines [1]; its project page frames the contribution as closing a gap in which reasoning (chain-of-thought) and acting (browsers, robots) had "remained separate" and documents the few-shot trajectory format of reason/act/observation triples [2]. HuggingGPT extended the controller idea across modalities, using ChatGPT to plan tasks, select models by their Hugging Face model-card descriptions, execute subtasks and summarise results [25]. The Augmented Language Models survey supplied the taxonomy that organises this period: reasoning as task decomposition and tool use as calling external modules, with augmentations combined "via heuristics" or learned from demonstrations [26]. A recent review of LLMs as autonomous agents and tool users, restricted to 2023-2025 A*/Q1 venues, reorganises this landscape around architectural design, single- versus multi-agent systems, tool integration strategies, and an analysis of 68 public datasets [27].

Toolformer marks the pivot from prompting to training: the model learns which APIs to call, when, with what arguments, and how to incorporate results, using self-supervision with only a handful of demonstrations per API, over a tool set that includes a calculator, a question-answering system, two search engines, a translation system and a calendar [3]. Gorilla attacked the same problem at API scale, releasing a fine-tuned LLaMA that the paper reports surpasses GPT-4 at writing API calls and that adapts to test-time documentation changes when combined with a document retriever, substantially mitigating hallucinations of API usage; it also introduced APIBench, built from HuggingFace, TorchHub and TensorHub APIs [28].

The interface itself was then standardised by vendors. OpenAI's June 2023 announcement introduced function calling in the Chat Completions API for GPT-4 and GPT-3.5 Turbo, where developers describe functions and the model outputs a JSON object of arguments; the models were fine-tuned both to detect when a function needs to be called and to respond with JSON adhering to the function signature, described via JSON Schema, and the November 2023 DevDay update added parallel function calling and JSON mode [5]. Google's Gemini API exposes the same convention as function declarations with name, description and typed parameters, supporting parallel as well as compositional/sequential calling and helpers that convert Python callables into declarations [6]. Gorilla's project page shows the open-model counterpart: OpenFunctions-v2 is trained for parallel and multiple-function selection across Java, REST and Python, and the Berkeley Function Calling Leaderboard (BFCL) began as roughly 2,000 question-function-answer pairs spanning Python, Java, JavaScript, REST and SQL, including function-relevance detection for unsuitable functions [29].

## Architectures: interleaved acting, learned invocation, and code as the action space

Three architectural families can be distinguished across the literature. Prompted interleaving (ReAct, its project-page trajectory format, and MRKL-style routing) keeps the model's weights fixed and encodes procedure in context [1][2][4]. Learned invocation (Toolformer, Gorilla, ToolLLaMA) changes the weights so that the decision to call, the argument construction and the use of the result are part of the model's generation distribution [3][28][11]. A third family makes executable code the single action space.

Code-as-action is the most consequential recent architectural shift. CodeAct consolidates agent actions into executable Python, executed by an interpreter so that the agent can revise prior actions or emit new ones from new observations across turns; the paper analyses 17 LLMs on API-Bank plus a new benchmark and reports up to 20% higher success rates than widely used JSON/text action alternatives, releases a 7,000-interaction instruction-tuning dataset (CodeActInstruct), and fine-tunes Llama 2 and Mistral agents that self-debug [30]. This idea is embedded in widely used scaffolds: OpenHands runs agents over an event stream against a Docker-sandboxed operating system containing a bash shell, a web browser and an IPython server, with a CodeActAgent as the default generalist and an AgentSkills toolbox auto-imported into the IPython environment, plus delegation actions for specialised sub-agents such as a browsing agent [31]. SWE-agent makes the complementary point that interface design, not model capability alone, determines performance: its agent-computer interface offers a small set of guarded actions (file search, a viewer window of at most 100 lines with scrolling, line-range editing, context management) and reaches 12.5% pass@1 on SWE-bench (12.47% of 2,294 tasks, 10.7 points above a Linux-shell-only baseline on the 300-instance subset) and 87.7% on HumanEvalFix, while remaining portable across models [18]. Multi-agent orchestration frameworks generalise this: AutoGen's v0.4 redesign uses an asynchronous, event-driven actor architecture with pluggable agents, tools, memory and models, provides an McpWorkbench for consuming Model Context Protocol servers and a Docker-based code executor, and its repository now points to Microsoft Agent Framework as the successor while remaining in maintenance mode [32].

Comparative evidence remains mixed on how much weight these scaffolds deserve. The post-training study below reports that a pretrained model with a light inference harness can behave as a capable agent despite far lower single-shot pass@1, which implies that scaffold and policy quality are partly substitutable and should be reported separately [33]. Benchmarks that measure only final outcomes and not trajectory quality make that substitution hard to quantify [34][35].

## Interfaces and protocols: JSON schemas, MCP, and agent-to-agent delegation

The vendor-level convention is now stable and cross-vendor compatible in shape rather than in wire format. OpenAI, Google and the Gorilla ecosystem all describe tools as typed declarations that the model selects and parameterises, with explicit support for parallel calls and for relevance detection when no tool fits [5][6][29]. What changed after 2024 is the emergence of a transport and discovery layer.

Anthropic released the Model Context Protocol in November 2024 as "a universal, open standard for connecting AI systems with data sources", with MCP servers exposing data and MCP clients connecting to them, shipped specifications and SDKs, local server support in Claude Desktop, and pre-built servers for Google Drive, Slack, GitHub, Git, Postgres and Puppeteer [7]. The protocol specification organises a server's surface into resources (context and data), prompts (templated messages and workflows) and tools (functions the model may execute), with optional opt-in extensions for asynchronous tasks, "skills over MCP", and embedded apps [36]. Discovery was formalised separately: the official MCP Registry is described as a centralised metadata repository for publicly accessible MCP servers backed by contributors including Anthropic, GitHub, PulseMCP and Microsoft, storing standardised `server.json` metadata with reverse-DNS names tied to verified GitHub accounts or domains, and exposing a REST API plus OpenAPI specification so that other registries can federate, with the explicit caveat that it is intended for aggregators rather than direct host consumption [37].

Tool interfaces and agent interfaces are converging. OpenAI's Responses API exposes a built-in MCP tool that connects to a remote server URL or a tunnelled local server, lists the server's tools as a dedicated output item, supports restricting imports with an allowed-tools list, and defaults to requiring human approval for MCP calls [8]. Google's A2A protocol, announced in April 2025 with more than 50 contributing partners including Atlassian, Box, Cohere, Intuit, LangChain, MongoDB, PayPal, Salesforce, SAP, ServiceNow, UKG and Workday, is explicitly positioned as complementing MCP, with capability discovery through a JSON Agent Card, a task lifecycle with artifacts, and a client/remote-agent interaction model [9]. A survey of four emerging interoperability protocols — MCP, ACP, A2A and ANP — describes MCP as providing a JSON-RPC client-server interface for secure tool invocation with typed exchanges, and argues that ad-hoc integrations are difficult to scale, secure and generalise [38]. An implementation-grounded comparison evaluates MCP-based and A2A-based implementations of the same software-engineering task, treating the choice as an engineering trade-off rather than a specification reading [10]. Security analysis of the same protocol field is less mature: one comparative threat-modelling study of MCP, A2A, Agora and ANP notes that security principles remain understudied and that no protocol-centric risk assessment framework has been established yet [39].

## Scaling to thousands of tools: retrieval, compression, and set-level selection

Once tool libraries grow past a few hundred entries, tool selection becomes an information-retrieval problem with an execution cost. ToolLLM is the canonical large-library setting: ToolBench was constructed from 16,464 real-world RESTful APIs spanning 49 RapidAPI Hub categories, with single- and multi-tool instructions and solution paths annotated by ChatGPT, a depth-first-search-based decision-tree method for exploring reasoning traces, an automatic evaluator (ToolEval), and a fine-tuned ToolLLaMA equipped with a neural API retriever that generalises zero-shot to an out-of-distribution tool-use dataset [11]. Gorilla's results provide the earlier evidence that retrieving the right documentation at inference time is what mitigates API hallucination [28].

Subsequent work splits into three strategies. Hierarchical retrieval with recovery: AnyTool operates over more than 16,000 APIs using a hierarchical retriever, a solver, and a self-reflection mechanism that re-activates the system when the initial solution proves impractical [12]. Candidate compression: Toollery targets settings with hundreds to tens of thousands of skills and tools where full-library prompting is costly, slow and less reliable, and presents a training-free framework that expands each tool specification into user-intent queries to build a retrieval index that maps requests to candidates [13]. Set-level selection: HYSET argues that existing retrievers either score tools in isolation or assemble the set sequentially, so the joint utility of a candidate set is never evaluated as a whole, and formulates pre-action selection as query-conditioned hyperedge prediction [14].

Evaluation of this layer is only now catching up. MCP-RADAR evaluates MCP-based tool use across five dimensions — answer accuracy, tool selection efficiency, computational resource efficiency, parameter construction accuracy and execution speed — and reports that leading commercial and open-source models trade these off against each other, which undermines single-metric rankings [40]. MCPMark stress-tests realistic MCP use with 127 expert- and AI-authored tasks that require create/read/update/delete operations and programmatic verification; under a minimal tool-calling loop the best reported model solved 52.56% of tasks at pass@1 and 33.86% at pass^4, with two other frontier systems below 30% pass@1, and tasks required on average 16.2 execution turns and 17.4 tool calls [41]. The practical lesson across these works is that library size, candidate-list quality and distractor design are part of the benchmark, not incidental setup [14][40][41].

## Acquiring tool-use skill: instruction tuning, RL, and distillation

Supervised agent tuning established that generalisation across tasks is possible but sensitive to data mixture. AgentTuning built AgentInstruct, 1,866 verified agent interaction trajectories with chain-of-thought rationales per decision step drawn from six agent tasks, and instruction-tuned the Llama 2 family into AgentLM-7B/13B/70B with a hybrid strategy that mixes agent data with high-quality general instructions; training on agent data alone improved held-in tasks but hurt generalisation, and the paper reports held-out improvements up to 170% with AgentLM-70B roughly matching GPT-3.5 Turbo on unseen agent tasks without degrading MMLU, GSM8K, HumanEval or MT-Bench [42]. ToolLLaMA follows the same recipe at API scale, with retrieval added to the tuned model [11], and CodeAct adds 7,000 multi-turn executable-action interactions for a code-action policy [30].

Reinforcement learning then reframed tool use as a policy-optimisation problem with unusual stability issues. TAO-RL reports that integrating external tools destabilises training — over-reliance induces input-distribution shift while excessive conservatism limits exploration — and couples tool-aware trajectory filtering with entropy-guided exploration [43]. Tool Zero claims that pure RL from scratch with dynamic generalisation-guided reward design outperforms supervised fine-tuning and SFT-then-RL pipelines on tool-agnostic generalisation [44]. Tool-R0 trains general tool-calling agents through self-play reinforcement learning without an initial dataset, reporting gains over base and supervised baselines [45], and a related framework combines self-evolving synthetic data with verifier-based RL for multi-turn interactive tool-using agents [46]. A survey of RL foundations for deep-research systems makes the general argument that RL addresses limitations of supervised and preference-alignment methods for tool interaction and exploration [47].

Two recent findings complicate the "more post-training is better" narrative. First, a study of the "sharpening tax" reports that on agentic tasks multi-turn tool use and interaction may require capabilities newly acquired during post-training rather than merely sharpened existing behaviour, and observes that pretrained models with a light inference harness can still serve as capable agents despite far lower pass@1 [33]. Second, distillation reverses the direction of transfer: SpatialOPSD, surfaced through the Hugging Face daily papers listing, explores whether a multimodal model can internalise agentic, tool-based capability so as to operate entirely tool-free, self-distilling from verified coding-agent traces (abstract-only evidence) [48]. Skill libraries provide a middle ground: ViSkill encodes successful interactions as composite visual skill cards directly accessible to the policy and optimises them jointly with RL, noting that prior skill approaches construct and update skills separately from policy optimisation (abstract-only evidence, also from the daily listing) [49]. Multi-turn behaviour is also not simply a by-product of better single-turn capability: MINT found that each turn of tool use yields only 1-8% absolute gains and each turn of natural-language feedback 2-17%, that better single-turn performance does not guarantee better multi-turn performance, and that supervised instruction fine-tuning and RLHF generally hurt multi-turn capability [50].

## Evaluation: environments, metrics, and their validity

Benchmarks for tool use began as API-calling suites. API-Bank provided a runnable evaluation system of 73 API tools and 314 annotated tool-use dialogues containing 753 API calls to assess planning, retrieval and calling, with a separate training set of 1,888 dialogues drawn from 2,138 APIs across 1,000 domains; its fine-tuned Alpaca-based model Lynx beat Alpaca's tool utilisation by more than 26 points and approached GPT-3.5, while GPT-4 excelled at planning [47]. BFCL scaled the same idea to thousands of functions with an Abstract Syntax Tree evaluation method, combining AST-substring and execution-response matching for single-turn calls, a pure AST matcher for crowd-sourced entries, state- plus response-based checkers for multi-turn interactions, and strict exact-match scoring for agentic tasks; the paper also runs a contamination check using perplexity ratios and concludes that state-of-the-art models excel at single-turn calling while memory, dynamic decision-making and long-horizon reasoning remain open [51].

Environment-style benchmarks shift the target from call syntax to task outcome. WebArena builds self-hosted, fully functional websites in four domains with tools and knowledge bases, scores functional correctness of long-horizon tasks, and reports 14.41% end-to-end success for the best GPT-4-based agent versus 78.24% for humans [15]. OSWorld evaluates 369 real computer tasks on Ubuntu, Windows and macOS with execution-based evaluation scripts, reporting humans above 72.36% against 12.24% for the best model, with GUI grounding and operational knowledge as the main obstacles [16]. GAIA posed 466 human-designed questions requiring reasoning, multimodality, browsing and tool use, released 166 with annotations and withheld the remaining 300 answers to prevent contamination, and reported 92% for human respondents against 15% for GPT-4 with (manually chosen) plugins, which it treats as an oracle upper bound [52]. SWE-bench turned software engineering into an execution task: 2,294 GitHub issues across 12 Python repositories, scored by applying the generated patch and running the fail-to-pass tests, where initial results were 1.96% (retrieval baseline), 0.00% for GPT-4 on a 25% subset, 0.70% for SWE-Llama, and 3.79% for Claude 3 Opus [53]. Tool-agent-user benchmarks add interaction: tau-bench simulates a user with a language model against domain APIs and policies and proposes pass^k, the probability that all k independent trials succeed; its abstract reports that state-of-the-art function-calling agents such as gpt-4o succeed on fewer than 50% of tasks and behave inconsistently, with pass^8 below 25% on the retail domain [54]. The paper's own experimental sections are reported to give per-domain pass^1 values of roughly 61% on tau-retail and about 35% on tau-airline for gpt-4o with function calling, at an approximate per-task cost of $0.38 for the agent and $0.23 for the user simulator; those specific figures come from the retrieving agent's reading of the paper rather than from text independently re-verified at abstract level, and should be treated as indicative rather than audited [54]. The official leaderboard shows the same pattern of fragile consistency and of scaffold effects: for the airline domain, tool-calling claude-3-5-sonnet reaches pass^1 0.460 and pass^4 0.225, gpt-4o 0.420 and 0.200, and prompted ReAct with gpt-4o only 0.325 and 0.160 [55].

Validity problems are documented in equal measure. SWE-bench+ found that 32.67% of SWE-Agent+GPT-4 successful patches involved solution leakage and 31.08% of passed patches were suspicious because of weak tests; removing those issues drops the resolution rate from 12.47% to 3.97%, and after building a post-cutoff, leakage-free dataset the same system scores 0.55%, with the strongest reported configuration (AutoCodeRover+GPT-4o) at 3.83% [17]. Trajectory scoring is contested too: AgentRewardBench, with 1,302 expert-reviewed trajectories across five benchmarks and 12 LLM judges, found that no single judge excels across benchmarks and that the rule-based evaluation used by common web benchmarks tends to underreport success rates [34]. Robustness is a separate axis: an assessment built on an expanded BFCL subset tests resilience to naturalistic query variations and stability as the toolkit grows with semantically related tools, and argues that existing evaluation methodologies have critical weaknesses for measuring this [56]. A survey of agent evaluation organises the field across core capabilities (planning, tool use), application benchmarks, generalist agents, benchmark dimensions and tooling, and identifies persistent gaps in cost-efficiency, safety and robustness assessment and in fine-grained, scalable evaluation methods [35]. Multi-turn protocols are also systematically under-measured, as MINT's finding that single-turn quality does not predict multi-turn quality makes explicit [50], and the review of agent and tool-user papers adds that dataset reuse is broad (68 datasets analysed) but rarely standardised across studies [27].

## Failure modes, security, and cost

Long-horizon reliability fails in ways that are now catalogued. Lost in the Middle documents a U-shaped context-position effect: accuracy is highest when relevant information sits at the beginning or end of the context, and middle placement can drop performance by more than 20%, with GPT-3.5-Turbo even falling below its closed-book level (56.1%) in multi-document QA; increasing retrieved documents from 20 to 50 improved that model by only about 1.5% and a contemporaneous long-context model by about 1%, while raising latency and cost [57]. That result matters directly for tool use, because retrieved tool documentation and accumulated tool outputs are exactly this kind of long, position-sensitive context [13][57]. Multi-agent scaffolds fail for structural reasons: the MAST taxonomy, built from 1,600-plus annotated traces across seven frameworks with high inter-annotator agreement (kappa = 0.88) over 150 analysed traces, identifies 14 failure modes in three categories (system design, inter-agent misalignment, task verification), notes that the performance gains of multi-agent systems on popular benchmarks are often minimal, and argues that most failures cannot be fixed by prompt tweaks [58].

Security evidence is quantitatively strong. AgentDojo populates a dynamic benchmark with 97 realistic tasks in email, banking and travel settings plus 629 security test cases, and reports that state-of-the-art models fail many tasks even without attacks while injection attacks violate some security properties but not all [59]. Agent Security Bench spans 10 scenarios, 10 agents, over 400 tools, 23 attack and defence methods and 8 metrics, covering prompt injection, memory poisoning, a plan-of-thought backdoor and mixed attacks over 13 backbone models and nearly 90,000 test cases, with a highest average attack success rate of 84.30% and limited effectiveness of current defences [19]. Exfiltration need not use code: LLMLeak describes a covert channel in which local malware that cannot reach the internet embeds a secret in a URL and presents the site as needed for a benign task, so that the agent's own web-fetch tool carries the secret to an attacker-controlled server, achieving a 79.7% attack success rate across eleven open-parameter models and evading defences aimed at code-based exfiltration (abstract-only evidence) [20]. The "lethal trifecta" gives the underlying capability structure: access to private data, exposure to untrusted content, and the ability to communicate externally, where removing any one leg prevents the attack, and where prompt-level warnings are described as an unreliable defence [60].

Mitigations span design, permissions and monitoring. CaMeL builds a protective layer that extracts control and data flow from the trusted query so that untrusted retrieved data cannot affect program flow, using capability metadata (provenance and allowed readers) enforced by a custom interpreter before every tool call; it reports solving 77% of AgentDojo tasks with provable security compared with 84% for an undefended system, and its guarantee depends on correctly extracting the trusted control flow [61]. The design-patterns study proposes six patterns for provable prompt-injection resistance — Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual LLM, Code-Then-Execute and Context-Minimization — around the principle that once an agent has ingested untrusted input it must be constrained so that the input cannot trigger consequential actions, and recommends sandboxing plus user confirmation for sensitive actions [62]. A paired-replay study of authorization gives the sharpest operational result: submitting identical model actions under broad-bearer credentials versus scoped JWT, sender-constrained and policy-engine conditions across 128 scenarios, harmful executions ranged from 8.9% to 37.8% under broad authorization and were zero under all three scoped conditions, though the authors stress that scoping contains consequences rather than preventing injection [21]. Step-level monitoring is complementary: ToolSafe trains a guardrail model with multi-task RL to check tool invocations before execution, and its feedback-driven reasoning framework is reported to reduce harmful tool invocations of ReAct-style agents by 65% on average while improving benign task completion by about 10% under prompt injection [22]. Detector-based defence, however, transfers poorly: a re-evaluation that replays ground-truth tool calls from AgentDojo and tau-bench to obtain benign-by-construction outputs found that the best detector on one benchmark caught only 2% of injections on another at a 1% false-positive rate, that a detector catching 72% on AgentDojo caught 15% elsewhere, and that false-positive rates ranged from none to above 90% [63]. Official guidance converges on the same controls: the OWASP Top 10 for Agentic Applications enumerates risks including Agent Goal Hijack, Tool Misuse and Exploitation, Identity and Privilege Abuse, Agentic Supply Chain Vulnerabilities, Unexpected Code Execution, Memory and Context Poisoning, Insecure Inter-Agent Communication, Cascading Failures, Human-Agent Trust Exploitation and Rogue Agents, and prescribes treating all natural-language inputs as untrusted, least-agency per-tool profiles, pinning and signing third-party tool packages or MCP servers, and human approval for high-impact actions [64].

Cost and latency are the least benchmarked axis. tau-bench's experiments report per-task costs for the agent and user-simulator models, which makes cost comparable across configurations in principle, though those figures were not independently re-verified for this survey [54]; a utility-guided orchestration study argues that free-form reasoning methods such as ReAct can raise task performance at the expense of excessive tool calls, longer trajectories, higher token consumption and latency, while fixed workflows are stable but inflexible, and proposes an explicit policy over actions such as respond, retrieve, tool-call, verify and stop that balances estimated gain, step cost, uncertainty and redundancy (abstract and introduction evidence) [65]. The agent-evaluation survey independently flags cost-efficiency as an under-assessed dimension [35], and MCPMark quantifies the execution profile that drives it, at about 16.2 turns and 17.4 tool calls per task [41].

## Trends and open problems

Four trends dominate the last two years of work. First, the action space has consolidated: prompted reason-act loops, JSON-schema function calls and executable code are increasingly combined in one scaffold, and code-as-action plus agent-computer-interface design currently deliver the largest reported gains from interface changes alone [1][5][30][18][31]. Second, tool access has been externalised into protocols and registries, moving the interesting engineering questions from "how does the model call a function" to discovery, federation, versioning and supply-chain trust [7][37][38][10][39][64]. Third, the scaling regime has shifted from model size to library size and data synthesis: retrieval, candidate compression and set-level selection compete to keep prompts small [11][13][14], while post-training increasingly relies on self-generated or verifier-scored trajectories rather than human annotation [43][45][46][33]. Fourth, safety has moved from prompt-level pleading to design-level constraint, with capability tracking, scoped credentials, sandboxing and pre-execution guardrails as the leading candidates [22][61][62][21][60].

Several problems remain genuinely open, and the evidence base is uneven.

- Evaluation validity. Contamination and weak tests can move headline numbers by an order of magnitude [17]; rule-based trajectory scoring underreports success [34]; tool-selection robustness to paraphrase and distractor tools is barely measured [56]; and agent evaluation still lacks fine-grained, scalable methods and cost accounting [35]. Benchmarks that evolve with adaptive attackers are one response, but they must themselves be maintained [59].
- Long-horizon and multi-turn reliability. Consistency decays faster than single-trial success, as pass^k results show [54][55], tasks require double-digit tool calls and turns [41], multi-turn competence is not implied by single-turn quality and is harmed by some standard alignment recipes [50], and degradation appears in long contexts of exactly the shape tool traces produce [57]. Multi-agent decomposition adds 14 documented failure modes that prompt engineering does not fix [58].
- Security guarantees versus utility. Undefended systems solve more tasks than provably-secured ones, and the gap is the price of enforcement [61]; scoped authorization removes harmful execution in one study but is explicitly not injection prevention [21]; detector-based defences transfer poorly across benchmarks [63]; and no protocol-centric risk framework exists yet for MCP, A2A, Agora or ANP [39]. The lethal trifecta framing suggests that some of this is best handled by capability denial rather than detection [60][64].
- Cost, latency and the harness/policy confound. Reported gains often conflate scaffold improvements with model improvements, and one recent study suggests the two are partly substitutable while attributing genuinely new capability to post-training only for multi-turn interaction [33]. Cost is reported sporadically [54] and only sometimes optimised explicitly [65].
- Evidence gaps in this survey's own base. The literature reviewed here is dominated by English-language benchmarks and by models released by a small number of vendors; several of the newest results were retrieved only at abstract level [44][45][46][33][48][49][65], quantitative full-text verification of tool-call schema error rates (as opposed to attack success rates and detector transfer) was not found, and one provider (the Hugging Face daily papers listing) surfaced only two relevant entries for this topic, so most Hugging Face coverage here comes from paper search rather than the daily feed [48][49].

The overall picture is of a field whose interface and protocol layer is standardising faster than its measurement layer. Tool-using agents are demonstrably capable on single-turn calls and short tasks, are unreliable on long-horizon, multi-turn and large-library settings, and are constrained primarily by evaluation validity, permission design and cost rather than by the raw ability to emit a correct function call [51][17][41][35][21].
